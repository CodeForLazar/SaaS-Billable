# Project Plan — Freelancer Client Portal

> **Single source of truth.** Read this before starting any work on the project.
> Update the **Progress** and **Decision log** sections at the end of every step.

## 1. What we're building

A multi-tenant SaaS where freelancers and small agencies manage **clients**, track **time** on **projects**, generate **invoices** from that time, and get **paid** online. Think a small version of Harvest or Bonsai.

The app is a **portfolio showcase** for GitHub and Upwork, so:

- The demo must be understandable within 10 seconds by a non-technical client.
- A **one-click demo login** with realistic seeded data is required. Reviewers won't sign up.
- The README and code quality matter as much as the features.

## 2. How we work

The developer knows Node.js well (builds dedicated Express-style servers) but hasn't used Next.js for a couple of years. So:

1. **Build piece by piece.** One small, focused step at a time. Don't scaffold whole features in one go.
2. **Explain before and while building.** Each step says what we're doing and why. New Next.js concepts are explained by comparing them to the Express/Node equivalent.
3. **Stop after each step** so the developer can review, run it and ask questions before we move on.
4. **Check the real docs.** Next.js 16 differs from older versions and from model training data. Read `node_modules/next/dist/docs/` before writing Next.js code. The same goes for Prisma and Better Auth: check the docs for the installed version.
5. **Keep this file current.** Tick off progress and record decisions as we go.

### Next.js 16 things to remember

- `middleware.ts` has been **renamed to `proxy.ts`**. Use it only for cheap, optimistic checks such as "has a session cookie → otherwise redirect". It is **not** where real authorization happens.
- **Cache Components** (`cacheComponents: true` + the `'use cache'` directive) is the new caching model. We decide whether to turn it on when we get to data fetching (see the decision log).
- Server Components are the default. Add `'use client'` only when a component needs state, effects or browser APIs.
- Mutations go through **Server Actions**. Use **Route Handlers** (`app/**/route.ts`) only for things that need a real HTTP endpoint: the Better Auth handler, the Stripe webhook, PDF download.
- **Errors:** *expected* errors (bad input, wrong password) are **returned** from actions and shown in the form; *unexpected* errors are **thrown** and caught by `error.tsx` boundaries. In Next 16 the boundary's "try again" is **`retry()`** (re-fetches), not `reset()`. In production, server error messages are replaced by a generic message + `digest` ID; the real error is logged via `instrumentation.ts` → `onRequestError`. Use `notFound()` for missing *or other-tenant* records.
- **Error pages in this app:** `app/(app)/[orgSlug]/error.tsx` (workspace pages; sidebar keeps working), `app/error.tsx` (everything else), `app/global-error.tsx` (root layout crashed; own `<html>`/`<body>`, system font, no app dependencies), `app/not-found.tsx` (unknown URLs + every `notFound()`, same wording for "doesn't exist" and "no access"). All share `components/error-state.tsx` and show the `digest` as "Reference"; they never show `error.message`. `instrumentation.ts` logs one JSON line per server error (`digest`, message, stack, method, path **without the query string**, route, type). `app/(app)/[orgSlug]/not-found.tsx` shows a missing (or other-workspace) record's 404 inside the shell.
- **Troubleshooting:** after a **schema change + `prisma generate`, restart `npm run dev`**. `lib/db.ts` keeps one Prisma client on `globalThis` across hot reloads, so a running dev server keeps the *old* client (symptom: `Cannot read properties of undefined (reading 'client')` for a new model).
- **`loading.tsx` wraps every page below it, and a streamed page can't send a 404 status** (headers are already sent as 200; Next only adds `noindex`). So a `loading.tsx` must not sit above pages that call `notFound()`: put it in a route group with only the page it's for (e.g. `clients/(list)/loading.tsx`, URL unchanged).
- **Troubleshooting:** if `next build` panics with `TurbopackInternalError … was canceled` (seen after a failed build), the build cache in `.next` is corrupted: `rm -rf .next` and build again.
- Nodemailer, Prisma and Better Auth all need the **Node.js runtime**, which is the default. Never use the Edge runtime for them.

### Rules

- **Tenant isolation:** every workspace page and service function starts with `requireMembership(orgSlug)` from `server/organizations.ts` (no session → `/sign-in`; not a member → `notFound()`, same as a non-existent workspace; else `{ session, organization, role }`). Every query on tenant data is scoped by `organizationId`. The service layer in `server/` takes the org ID from the verified session and membership, **never from client input**. Pages and actions call `server/*`, not Prisma directly.
- **Permissions:** `can(role, { resource: ['action'] })` from `lib/permissions.ts`: Better Auth's default roles (owner: everything; admin: everything except deleting the workspace; member: no management rights) **extended with our own resources** via `createAccessControl` (`client` and `project`: create/update/archive for owner + admin; members read only). The same `ac` + `roles` are passed to the `organization()` plugin, so Better Auth and our code share one definition. **Add each new resource there.** Handles combined roles (`"admin,member"`); unknown roles get nothing. In the browser it only hides UI; the server checks again. Pages a role can't use call `notFound()`.
- **Server Actions with a bound argument** (`action.bind(null, orgSlug)`): bound values are sent by the browser and can be tampered with, so treat them as input (the service re-checks them with `requireMembership`).
- **After a mutation**, call `refresh()` from `next/cache` in the Server Action to re-render the current page's server data (Next 16). `revalidatePath`/`revalidateTag` are for invalidating *cached* data.
- **Authorization lives next to the data.** Every server action and service function checks the session and the user's role. `proxy.ts` is only a convenience redirect.
- **Money** is stored as integer **cents**; the workspace's currency is in its billing settings (`WorkspaceSettings`), and each invoice copies it. Quantities are integer **hundredths** (650 = 6.50 h).
- **Time** is stored in UTC. Durations are stored in **seconds**.
- **Validation:** every server action parses its input with Zod before touching the DB.
- **Code style:** enforced by **Prettier** (`.prettierrc.json`): 100 columns, 3-space indent, single quotes (also in JSX), no trailing commas; JSON keeps 2 spaces. `npm run format` / `npm run format:check`. Not formatted: `components/ui/` (shadcn), generated code, migrations, Markdown (`.prettierignore`). Run `npm run format` before committing. Exception: `components/ui/*` is generated by shadcn and keeps its own formatting.
- **Public pages:** `proxy.ts` treats every path as protected except `PUBLIC_PATHS` (exact) and `PUBLIC_PREFIXES` (e.g. `/accept-invitation/`). **Add every new public page** (e.g. the public invoice page `/i/[token]` in Phase 5, the landing page's sub-pages) **to `PUBLIC_PATHS`**, or signed-out visitors get redirected to `/sign-in`.
- **Reserved slugs:** workspace URLs live at the site root (`/<slug>/…`), so `lib/slug.ts` has `RESERVED_SLUGS`. **Add every new top-level route in `app/` to that list.**
- **Base UI data attributes differ from Radix:** e.g. `data-vertical:` / `data-horizontal:` (not `data-[orientation=vertical]:`), `data-popup-open:` (not `data-[state=open]:`). Check the component's own classes before copying Radix-era shadcn examples.
- **Menu radio items close the menu only with `closeOnClick`** (Base UI default: stay open). Use it for single-choice actions like picking a role.
- **Buttons that submit need `type='submit'`**: Base UI's `Button` defaults to `type='button'`, which never submits a form (a `formAction` on it silently does nothing).
- **Theme:** emerald, defined only as CSS variables in `app/globals.css` (`--primary` = Tailwind emerald-700, tinted grays, emerald charts; a matching `.dark` set for a future toggle). All text/background pairs meet WCAG AA 4.5:1; don't use emerald-600 behind white text (3.7:1). Emails can't read CSS variables, so their buttons use `bg-emerald-700` directly.
- **Dropdown fields use shadcn `Select`** (Base UI), not a native `<select>`: its list is positioned by the page next to the field, the same on every device (native select popups land in the wrong place in DevTools' mobile view). Give it `name` (adds a hidden input for forms) and `items` (so the field shows the label, not the raw value).
- **Tables on phones:** hide secondary columns below `sm` (`hidden sm:table-cell`) and show key details under the main cell, so tables don't scroll sideways (a sideways-scrolled table pushed the ⋯ menu off-screen).
- **UI:** build pages from shadcn components (`components/ui`). A link styled as a button: `className={cn(buttonVariants({ variant }))}`. Without `cn()` the base and variant classes conflict (e.g. no outline border). Use theme colors (`bg-background`, `text-muted-foreground`, `bg-primary`...) instead of raw Tailwind colors so dark mode and theming work.
- **Secrets** live in `.env` (git-ignored). Every variable is documented in `.env.example` **and typed in `env.d.ts`** (editor autocomplete for `process.env`).

## 5. Data model (draft)

Better Auth generates and owns: `User`, `Session`, `Account`, `Verification`, and through the organization plugin `Organization`, `Member`, `Invitation`, all in `prisma/schema/auth.prisma`. We extend `Organization` with app settings.

Our own models each go in their own file in `prisma/schema/` (e.g. `client.prisma`).

Our own models (all carry `organizationId`):

| Model | Key fields |
|---|---|
| **WorkspaceSettings** ✅ | 1:1 with `Organization` (`organizationId` is the key), created on first save: `currency`, business name/email/address (invoice sender), `invoicePrefix`, `nextInvoiceNumber`, `paymentTermsDays`, `taxRateBasisPoints` (2000 = 20 %). Its own table, not columns on Better Auth's `Organization`. CHECK: counter ≥ 1, terms 0–365, tax 0–100 %. |
| **Client** ✅ | `name`, `email?`, `company?`, `address?`, `notes?`, `archivedAt?` (archive, don't delete); `@@unique([id, organizationId])` for the composite FK |
| **Project** ✅ | `clientId`, `name`, `hourlyRateCents?`, `color?`, `archivedAt?` (instead of a status enum, same as clients). **Composite FK** `(clientId, organizationId)` → `Client(id, organizationId)`: the DB guarantees a project's client is in the same workspace. `onDelete: Restrict` on the client. |
| **TimeEntry** ✅ | `projectId` (composite FK within the workspace, `Restrict`), `userId` (`Restrict`: time never vanishes with an account), `description?`, `startedAt`, `endedAt?` (null = timer running), `durationSec?` (set exactly when ended), `billable`, `invoiceLineId?` (set = billed: locked; SetNull when the line or draft is deleted). **One running timer per user** = partial unique index `time_entry_one_running_timer_per_user` (`userId` WHERE `endedAt` IS NULL, Prisma preview feature `partialIndexes`). CHECK constraints added by hand in the migration: `endedAt >= startedAt`, duration set ⇔ ended. |
| **Invoice** ✅ | `clientId` (composite FK, `Restrict`), `status` DRAFT/SENT/PAID/VOID (**overdue is computed**: SENT + due date before today), `number?` (given when **sent**, unique per workspace), `currency`, `issueDate?`/`dueDate?` (`@db.Date`), `paymentTermsDays`, `taxRateBasisPoints`, `notes?`, `subtotalCents`/`taxCents`/`totalCents` (recalculated with every line change), **snapshots** `from*`/`billTo*` (taken when sent), `publicToken?` (unique, 192 random bits, set when sent), `sentAt?`/`paidAt?`/`voidedAt?`, `lastReminderAt?` + `reminderCount` (payment reminders). CHECKs: a draft has no number; anything issued has number + token + dates; paid ⇒ `paidAt`, void ⇒ `voidedAt`; total = subtotal + tax; reminder count and date go together. |
| **InvoiceLine** ✅ | `invoiceId` (composite FK with `organizationId`, cascade), `position`, `description`, `quantityHundredths`, `unitPriceCents`, `amountCents` (= round(qty × price)). CHECK: qty > 0, price/amount ≥ 0. `TimeEntry.invoiceLineId` (SetNull) = the time this line bills. |
| **Payment** ✅ | `invoiceId` (composite FK, cascade with the workspace), `amountCents` + `currency` (in the **invoice's** currency), `stripeCheckoutSessionId` (**unique**: makes recording idempotent), `stripePaymentIntentId?`, `paidAt`. Only successful payments are recorded. CHECK: amount > 0. |

IDs of our own models: `@default(cuid(2))`. Reverse relations on `Organization` (`clients`, `projects`) are hand-added in `auth.prisma` (verified the Better Auth CLI keeps them when it rewrites the file).

Reverse relations for `TimeEntry` are hand-added on `User` and `Organization` in `auth.prisma` too (the CLI keeps them).

Relationships: Organization → Clients → Projects → TimeEntries. Invoice → InvoiceLines ← TimeEntries (once billed). Invoice → Payments.

We'll refine this (indexes, constraints, enums) in the schema step and keep this table in sync.

## 6. Auth design (Better Auth)

- **Sessions** are stored in the DB (`Session` table). The browser holds an HTTP-only cookie with the session token. Optionally we enable the cookie cache to skip the DB lookup on each request.
- **Endpoints** are served by one catch-all route handler: `app/api/auth/[...all]/route.ts`.
- **Schema changes** (e.g. adding a plugin): `npm run auth:generate` writes Better Auth's models into `prisma/schema/auth.prisma` (the file must exist, or the CLI creates a full standalone schema), then `npm run db:migrate -- --name <name>` creates and applies the migration. Better Auth's own `migrate` command is not used with Prisma.
- **Migrations when `migrate dev` needs confirmation** (e.g. adding a unique constraint prints a warning and prompts): in a non-interactive shell, write the SQL with `prisma migrate diff --from-config-datasource --to-schema prisma/schema --script` into `prisma/migrations/<UTC timestamp>_<name>/migration.sql`, then run `prisma migrate deploy`.
- **Server side:** `auth.api.getSession({ headers })` in Server Components, Server Actions and Route Handlers. This is our `req.user`.
- **Client side:** `authClient.signIn.email()`, `signUp.email()`, `signOut()`, `useSession()`.
- **Email/password** with verification email and password reset. Both call our `sendEmail()` (Nodemailer).
- **Email verification is required:** sign-up creates the user but no session and redirects to `/check-email`. The link (`/api/auth/verify-email?...&callbackURL=/sign-in`) marks the email verified and signs the user in; `/sign-in` forwards signed-in users to the app, and shows a message for `?error=INVALID_TOKEN|TOKEN_EXPIRED`. Signing in unverified is rejected (`EMAIL_NOT_VERIFIED`) and sends a fresh link. Links expire after 1 hour.
- **No email enumeration:** sign-up with an existing email returns the same response as a new one (Better Auth behaviour when verification is required).
- **Password reset:** `/forgot-password` → `requestPasswordReset` (same response for unknown emails) → email link `/api/auth/reset-password/<token>?callbackURL=/reset-password` → Better Auth forwards to `/reset-password?token=…` (or `?error=INVALID_TOKEN`) → `resetPassword` → `/sign-in?reset=success`. Tokens are single-use, expire after 1 h; a reset **revokes all sessions** and marks the email verified.
- **Emails are sent in the background** via `advanced.backgroundTasks.handler` → Next's `after()`: the response doesn't wait for SMTP (no timing leak) and serverless hosts keep running until the email is sent.
- **Organization plugin:** create a workspace on sign-up, invite members by email, roles `owner`/`admin`/`member`. Tables: `organization` (unique `slug`), `member` (user ↔ organization + `role`, a plain string), `invitation`. The creator becomes `owner`. `session.activeOrganizationId` remembers the last-used org, but **the URL slug is the source of truth** for which org a request is about.
- **`proxy.ts`** (Next 16's middleware, Node.js runtime): if the path isn't public and there's **no session cookie** (`getSessionCookie`, handles the `__Secure-` prefix), redirect to `/sign-in`. It never validates the cookie or touches the DB; forged/expired cookies pass and are rejected by the pages. It does **not** redirect signed-in users away from auth pages (an expired cookie would loop). Matcher skips `/api/`, `_next/static`, `_next/image` and files with an extension.
- **Routing:** `/dashboard` is only a redirect ("take me to my workspace"): `user.lastActiveOrganizationId` (if still a member) → first membership → `/create-workspace`. `/[orgSlug]` → `/[orgSlug]/dashboard`.
- **Last-used workspace:** `user.lastActiveOrganizationId` is a Better Auth `additionalField` with `input: false` (clients get `FIELD_NOT_ALLOWED` if they try to set it). `app/(app)/[orgSlug]/layout.tsx` updates it with `after()` when the workspace changes. (We don't rely on `session.activeOrganizationId`: every sign-in starts a new session.)
- **Workspace switcher** (`components/workspace-switcher.tsx`, client): data comes from the server as props; switching = navigating to `/<slug>/dashboard`. Uses `DropdownMenuLinkItem`, a small addition to `components/ui/dropdown-menu.tsx` wrapping Base UI's `Menu.LinkItem` with `render={<Link />}`.
- **`server/` modules start with `import 'server-only'`**: importing them from a Client Component fails the build (verified).
- **Note:** deleting a user removes their memberships (cascade) but **not** organizations they own; handle that explicitly if we add account deletion.
- **Invitations:** owners/admins invite by email with role `member` or `admin` (`INVITABLE_ROLES`; owner is not invitable). `server/members.ts` `inviteMember()` checks membership + `can(role, { invitation: ['create'] })`, then `auth.api.createInvitation` with the org ID from the membership. Better Auth enforces it again (members → 403, admins can't invite owners, no duplicates, 48 h expiry, max 100 pending) and calls `sendInvitationEmail` (`emails/invitation.tsx`) with a link to `/accept-invitation/<id>` (reserved slug; must become a public path in step 3).
- **`redirectTo` after sign-in/sign-up:** `/sign-in?redirectTo=/path&email=…` (links built with `authHref()`). Always passed through `safeRedirectPath()` (`lib/safe-redirect.ts`): only same-site paths, everything else is dropped (**open-redirect protection**; tested against `https://`, `//`, backslash, tab and `javascript:` tricks). The email-confirmation link carries it too (`callbackURL=/sign-in?redirectTo=…`), so new users return to where they started.
- **Accepting invitations:** `/accept-invitation/[id]` is public. `server/invitations.ts` reads the invitation (pending + not expired); the page shows: invalid → message; signed out → sign in / create account (email pre-filled, `redirectTo` back); wrong account → "sign in as <invitee>" (signs out first); invitee → Accept/Decline (Better Auth checks recipient + verified email). Already a member → straight to the workspace.
- **Managing members** (`/[orgSlug]/settings/members`): per-row "⋯" menu (change role, remove with confirmation), cancel invitation, leave workspace. The server computes which actions each row offers (no menu on your own row; only owners see/touch owners; only owners can assign `owner`). Better Auth enforces: permissions, only owners change/remove owners or grant owner, **never zero owners** (demote/remove/leave). Service functions in `server/members.ts` map its error codes to friendly messages. Feedback via toasts (`sonner`, `<Toaster theme='light' />` in the root layout).
- **Calling Server Actions from event handlers** (not forms): `startTransition(async () => { const r = await action(...); toast(...) })`. Plain arguments, validated with Zod in the action; `refresh()` updates the page.
- **App shell** (`app/(app)/[orgSlug]/layout.tsx`): `SidebarProvider` (open/collapsed in the `sidebar_state` cookie, read on the server so there's no flash) → `AppSidebar` (client, highlights the current page; `WorkspaceSwitcher` on top, nav groups, `NavUser` at the bottom with sign-out) + `SidebarInset` (renders `<main>`, so **pages use a `<div>`**, not `<main>`) with `AppHeader` (toggle + breadcrumb from the URL, labels in `app-header.tsx`). **Nav only lists pages that exist**: add each new section to `navGroups` in `components/app-sidebar.tsx` (and its label to `AppHeader`). Ctrl/Cmd+B toggles the sidebar; on phones it's a drawer that closes when a link is tapped.
- **Product name** (working name "Billable") and pitch live in `lib/site.ts`. Page titles use the root layout's template: pages set `title: 'Sign in'` → "Sign in · Billable".
- **Landing page** `app/(marketing)/page.tsx` with `(marketing)/layout.tsx` (header: Sign in / Get started, or Go to dashboard when signed in; footer). Screenshots/GIF and the demo-login button come in Phase 8.
- **List pages** (clients, projects): filters and paging live in the **URL** (`?q=…&status=archived&page=…`), parsed with `listQuerySchema` (`lib/validations/list.ts`; `.catch()` falls back to defaults for junk values), rendered by the Server Component. Shared Server Components in `components/list-controls.tsx`: `ListSearch` (`next/form` GET form, works without JS, keeps the status), `StatusTabs` (Active/Archived links) and `ListPagination`; links built with `listHref()`. Service functions count first and clamp the page. 20 per page; sort by name with `id` as tie-breaker. `(list)/loading.tsx` gives a skeleton while the list loads. Shared date formatting in `lib/format.ts`.
- **Record pages** (client, project): back link, title + badges, Edit / Archive buttons shown by `can()`, details in `components/detail-list.tsx`.
- **Archiving** (never deleting) clients and projects: `components/archive-button.tsx` (confirm dialog for Archive, none for Restore; toast), given a Server Action with the record bound (`setClientArchivedAction.bind(null, orgSlug, id)`). **Archiving a client archives its active projects with the same timestamp** (one `$transaction`); restoring the client restores exactly those, projects archived separately stay archived. A project can't be restored while its client is archived, and archived clients can't get new projects.
- **Money input:** `lib/money.ts`: rates are typed as text (`75.50`), checked with `MONEY_PATTERN` and converted to cents by `inputToCents()` (string parsing, no float maths), shown with `formatMoney()` / `centsToInput()`. The currency comes from `getWorkspaceSettings(orgSlug).currency` (default `DEFAULT_CURRENCY`, USD); money fields use `components/money-input.tsx` (currency symbol in an input group, so "CHF" fits as well as "$"). Only 2-decimal currencies are offered (`CURRENCIES`).
- **Project colors:** a fixed palette in `lib/project-colors.ts` (hex values stored on the project, validated with `z.enum`), picked with visually hidden native radio buttons (keyboard works), shown with `components/color-dot.tsx`.
- **New routes and `PageProps<'…'>` types:** the route types are generated by `next dev` / `next build`; after adding a route without either running, `npx next typegen` refreshes them (otherwise `tsc` says the route "does not satisfy the constraint 'AppRoutes'").
- **Create/edit forms** (clients now, projects next): one shared form component (`clients/client-form.tsx`, `useActionState`) for both pages; the action is bound to the workspace (and record id) by the page; on success the action `redirect()`s to the record's page, on error it returns the typed values + errors. Optional text fields are trimmed and stored as `NULL` when empty. Services check `can()` and return a friendly error; updates use `updateMany({ where: { id, organizationId } })` so another workspace's id matches nothing. Record lookups (`getClient`) are `cache()`d so the page and `generateMetadata` share one query.
- **Dates with date-fns:** work in the user's zone with `new TZDate(ms, timeZone)` / `TZDate.tz(timeZone)` or the `{ in: tz(timeZone) }` option; calendar maths (`subDays`, `startOfWeek` with `weekStartsOn: 1`, …) then respects daylight saving (a day isn't always 24 h: never subtract `24 * 60 * 60 * 1000`). Pass plain `Date`s to Prisma. `lib/format.ts` wraps `format` so pages keep calling `formatDate`/`formatTime`/`dayKey`/`formatWeekday`, plus `formatRelative(date, requestNow())` ("in 2 days"). **Always pass the user's `timeZone`** (from `getTimeZone()`) to these helpers, also for "Added" dates: without it the server's zone is used (UTC on Vercel), which can show the next day.
- **Time zones:** the DB stores UTC. The browser's zone is stored in a `tz` cookie by `components/time-zone-sync.tsx` (in the workspace layout; refreshes once when it changes); `getTimeZone()` (`lib/time-zone.ts`) reads it on the server (fallback UTC) and pages pass it to `formatTime` / `dayKey` / `formatWeekday` (`lib/format.ts`). "Today", day groups and (later) weeks are computed in that zone. `requestNow()` is one `Date.now()` per request (React's purity lint rejects `Date.now()` in render).
- **Timer:** one per user across all workspaces. `startTimer` stops the running one first (interactive `$transaction`); a concurrent second start hits the partial unique index (`P2002`) and gets a friendly error. `stopTimer()` takes no workspace: it stops the signed-in user's own timer from anywhere. The running timer is loaded by the workspace layout and shown in the header (`RunningTimer`, via an `AppHeader` children slot) on every page, linking to the workspace it runs in; start/stop call `refresh()`, which re-renders the layout too. Live duration: `components/elapsed.tsx` (`useSyncExternalStore` 1 s clock; server snapshot = `renderedAt` so hydration matches).
- **Everyone tracks their own time:** time services only touch the signed-in user's entries (members included; no `can()` check needed). Viewing/editing other people's time is for later (timesheet/reports).
- **Manual entries** (Time page, "Add time" tab; edit at `/time/[entryId]/edit`, delete from the entry's ⋯ menu with confirmation): a date + From/To on the user's clock, same day only (an entry can't cross midnight: split it). `lib/zoned-time.ts` converts between wall-clock time in a zone and UTC (`zonedToUtc`, `utcToZoned`, built on `TZDate`); daylight saving: a skipped hour moves forward, a repeated hour takes the first. The service rejects an end that lands before the start after conversion. Only your own **finished** entries can be edited/deleted (someone else's, another workspace's or a running timer → 404 / "no longer exists"). Editing keeps the entry's project selectable even if archived; new entries need an active project.
- **`'use client'` modules export only components/props to the server:** a Server Component can *render* a client component, but *calling* a plain function exported from a `'use client'` file throws at runtime ("Attempted to call X() from the server"), and neither `tsc` nor lint catch it. Keep shared helpers in plain modules (e.g. `time/group-projects.ts` next to `project-select.tsx`).
- **Weekly timesheet** (`/[orgSlug]/time/week?week=<any day>`, "Entries / Week" `LinkTabs` on both Time pages): my finished entries per project (rows) and day (Mon–Sun) with day, week and billable totals. The week is computed on the user's clock (`startOfWeek(new TZDate(…, zone), { weekStartsOn: 1 })`, up to `addWeeks(monday, 1)`: a daylight-saving week is 167/169 h); an entry counts for the day it **started** on. Junk `?week=` → this week. From `md` up a table; on phones a list per day (`hidden md:block` on a wrapper: shadcn `Table` renders its own container div, so hiding the `<table>` leaves an empty box).
- **`LinkTabs`** (`components/link-tabs.tsx`): tabs that are links (each tab its own URL, server-rendered); `StatusTabs` and `TimeTabs` use it.
- **Invoices** (owners and admins: the `invoice` resource; members get 404 everywhere, even the nav link is hidden). Lifecycle: **draft** (created from a client's unbilled billable time, one line per chosen project at the project's rate, plus manual lines; lines/tax/terms/notes editable; deletable) → **sent** (`issueInvoice`: next number from the row-locked `nextInvoiceNumber` counter, issue date = today on the user's calendar, due = + terms, snapshots, public token; optionally emailed) → **paid** (by hand now, Stripe in Phase 6) or **void** (kept with its number; its time becomes unbilled again). Services in `server/invoices.ts`; every draft edit re-checks `status: 'DRAFT'` and recalculates totals in the same transaction. Creating a draft **claims** the time with `updateMany({ where: { id: in ids, invoiceLineId: null } })`: if another draft took some of it, the count is short and everything rolls back. Billed time is locked on the Time page ("Invoiced" badge, no menu, edit page 404, service refuses).
- **Invoice display:** `lib/invoice-view.ts` `toInvoiceView()` = what's printed (drafts: current business/client details; sent: the snapshot), used by `components/invoice-document.tsx` (app + public page) and `lib/invoice-pdf.tsx` (PDF), so they never disagree. `lib/invoice-status.ts`: display status incl. **overdue**, labels, badge variants. Issue/due dates are `@db.Date` (UTC midnight): format them with `DATE_ONLY_ZONE` ('UTC'), never the user's zone.
- **Sending:** `sendInvoiceAction` issues first, then emails (`emailInvoice`: PDF attached, reply-to = business email, link to `/i/<token>`); an email failure is a warning, not a failure ("Resend email" exists). A clash with a used number (counter set back in settings) → friendly error, nothing changes.
- **PDF:** `@react-pdf/renderer` (auto-external in Next); `invoicePdfResponse()` for the route handlers `/[orgSlug]/invoices/[invoiceId]/pdf` and `/i/[token]/pdf` (`private, no-store`). Font **Noto Sans** from `lib/fonts` (Helvetica has no Cyrillic and a broken € width). The fonts are read from disk, so `next.config.ts` `outputFileTracingIncludes` ships them with those routes; **route keys escape dynamic brackets** (`'/\\[orgSlug\\]/invoices/**'`), and the `.nft.json` files under `.next/server/app/(app)/...` show what's included.
- **Public invoice page** `/i/[token]` (in `PUBLIC_PREFIXES`, `i` reserved): no shell, `noindex`, `referrer: no-referrer`; unknown/junk token or a draft → 404; shows due/overdue/paid/void notices. Overdue there is judged on UTC's calendar (the visitor's zone is unknown).
- **A section guard layout** (`invoices/layout.tsx`): a permission check in a *layout* runs before a child `loading.tsx` starts streaming, so members get a real 404 status. Pages and services still check (layouts don't re-run on client navigation).
- **Nav items can require a permission** (`permission` in `navGroups`, checked with `can()`); Invoices and Settings › Billing use it.
- **`ConfirmActionButton`** (`components/confirm-action-button.tsx`): "are you sure?" + a bound Server Action + toast; used for invoice status changes. Dialog forms (`invoices/[invoiceId]/line-dialog.tsx`) wrap the action to close on success, and keep the form inside the dialog content so it resets on every opening.
- **Online payments (Stripe Checkout):** the public invoice shows "Pay €…" (`app/i/[token]/pay-button.tsx`, a form + Server Action) → `createCheckoutSession(token)` (`server/payments.ts`: only SENT invoices, full amount, Stripe's minimum per currency in `lib/stripe.ts`, `adaptive_pricing: { enabled: false }` so the client pays in the invoice's currency, invoice id in `metadata`) → `redirect()` to Stripe's hosted page. Back: `success_url` = the Route Handler `/i/[token]/paid?session_id=…` (writes, so not a page), which **fetches the session from Stripe** and records it if paid and it belongs to this invoice, then redirects to `/i/<token>?payment=paid|processing` (or no message); `cancel_url` → `?payment=cancelled`. The URL parameter only picks a message, never data.
- **Stripe webhook** `app/api/stripe/webhook/route.ts`: reads the **raw body** (`request.text()`), `constructEvent` with `STRIPE_WEBHOOK_SECRET` (bad/missing signature → 400), handles `checkout.session.completed` + `async_payment_succeeded`, always 2xx otherwise (Stripe retries non-2xx for 3 days). Both paths call `recordCheckoutPayment()`: idempotent via the unique session id (P2002 = already recorded), compares amount + currency with the invoice (using `currency_conversion` source amounts if Stripe ever converted), SENT → PAID in the same transaction; a void invoice stays void (money still recorded, logged).
- **Stripe locally:** `STRIPE_SECRET_KEY` (sk_test_) and `STRIPE_WEBHOOK_SECRET` in `.env` (see `.env.example`); `stripe listen --print-secret` gives the local whsec; run `stripe listen --events checkout.session.completed,checkout.session.async_payment_succeeded --forward-to localhost:3000/api/stripe/webhook` while testing (CLI 1.52 requires `--events`). Test card 4242 4242 4242 4242. The Stripe client is created lazily (`getStripe()`), so builds don't need the key.
- **Payment reminders** (invoice page, "Send reminder" on a SENT invoice with a client email): `sendInvoiceReminder` in `server/invoices.ts` emails `emails/invoice-reminder.tsx` ("is overdue" / "is due on …", judged on the sender's calendar; PDF attached, reply-to the business, "View and pay" link). **At most one per 24 h** (`REMINDER_INTERVAL_HOURS`): the service *claims* the reminder with a conditional `updateMany` (`lastReminderAt` null or older than 24 h) **before** sending, so simultaneous clicks send one email; if the email fails the claim is given back and the user sees "could not be sent". The page shows "Overdue since …" and when the last reminder went out.
- **Don't wrap service calls in `try/catch` in actions:** `requireMembership()`'s `notFound()` works by throwing; a catch-all swallows it (an outsider got "could not be sent" instead of a 404). Catch only around the risky call (e.g. sending the email) inside the service.
- **Base UI `Checkbox`:** submits `"on"` when ticked, nothing when not; its `id` lands on the hidden input, so a `FieldLabel htmlFor` works for clicking.
- **Demo login:** a button that signs into the seeded demo account. The demo data is reset periodically, or protected from destructive actions (decide later).
