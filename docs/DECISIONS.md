# Decisions

The main technical decisions, with the reasoning at the time. Newer rows can replace older ones (struck through).

| Date | Decision | Why |
|---|---|---|
| 2026-09-25 | App idea: freelancer client portal (clients, time, invoices, payments) | Relatable to Upwork clients; rich relational data; covers the full stack |
| 2026-09-25 | Prisma over Drizzle | Mature migrations and tooling, a readable schema file, and typed queries without writing SQL for everyday work |
| 2026-09-25 | Better Auth over Auth.js | Built-in email/password, DB sessions, organization plugin; Auth.js is now maintained by the Better Auth team, who recommend Better Auth for new projects |
| 2026-09-25 | Nodemailer (SMTP) over Resend SDK | Works with any provider (Mailpit locally, Resend in production) instead of tying the code to one vendor's SDK |
| 2026-09-25 | Org scoping via `[orgSlug]` in the URL | Explicit, shareable URLs; clear tenant boundary. Can revisit. |
| 2026-09-25 | Prisma **7.10.0**, pinned exact | npm `latest` tag for `prisma` points to 8.0 RC; `@prisma/client` latest is 7.10. Stay on stable. Note: prisma.io docs now describe v8. |
| 2026-09-25 | Config file named `prisma.config.ts` | `prisma init` 7.10 generated `prisma7.config.ts`; the standard name loads fine and is what docs/tools expect |
| 2026-09-25 | No `import 'server-only'` in `lib/db.ts` | Scripts outside Next (seed, Better Auth CLI) import it; put `server-only` on `server/*` modules instead |
| 2026-09-25 | First migration deferred to Better Auth step | Avoid a throwaway model; auth tables are the first real schema |
| 2026-09-25 | Ignore `npm audit` highs from the Prisma CLI (`deepmerge-ts`, `mysql2`) | Dev-only CLI deps, not shipped; `audit fix --force` would downgrade to Prisma 6. Recheck on Prisma upgrades. |
| 2026-09-25 | Better Auth **1.7.6**, pinned exact; CLI via `npx auth@1.7.6` (`auth:generate` script) | The old `@better-auth/cli` package is stale (1.4); the CLI now ships as the `auth` package. Pin CLI to the library version. |
| 2026-09-25 | Nodemailer **10.0.10** + React Email **6.11.0** (single `react-email` package), pinned | `@react-email/components` is deprecated; v6 exports components and `render` from `react-email`. Nodemailer 10 ships its own types, so no `@types/nodemailer`. |
| 2026-09-25 | Auth forms call **Server Actions** that use `auth.api.*`, not the browser `authClient` | Matches our "mutations via Server Actions + Zod" rule; forms work without JS; errors handled on the server. `authClient` stays available for client-only needs (e.g. `useSession`). |
| 2026-09-25 | Auth checks in **pages** (and later the service layer), not layouts | Next docs: layouts don't re-render on navigation, so a layout check can be skipped |
| 2026-09-25 | Zod **4.6.5**, pinned | Current major; use `z.email()`, `z.flattenError()` |
| 2026-09-25 | shadcn **`base-nova`** preset (Base UI underneath) | Current shadcn CLI default. Components look the same as the Radix version; examples online may use Radix's `asChild` where Base UI uses a `render` prop. |
| 2026-09-25 | shadcn's **`cn` package** instead of `clsx` + `tailwind-merge` | Added by the CLI; official shadcn package (github.com/shadcn-ui/cn). `lib/utils.ts` re-exports it. |
| 2026-09-25 | Dark mode is **class-based** (`.dark` on `<html>`), not OS-based | shadcn's theme uses `@custom-variant dark`. The app is light-only for now; a theme toggle can use the existing `.dark` colors. |
| 2026-09-25 | Inputs refilled after a failed action use `key={value}` | Base UI warns when an uncontrolled input's `defaultValue` changes; a key remounts it instead |
| 2026-09-26 | **Require email verification** before sign-in | Realistic SaaS flow; prevents fake sign-ups and enumeration. Seeded demo account will be pre-verified. |
| 2026-09-26 | Better Auth background tasks run through Next's **`after()`** | Don't block responses on SMTP; works on serverless (Vercel) without `@vercel/functions` |
| 2026-09-26 | Type env vars with a hand-written **`env.d.ts`** (`NodeJS.ProcessEnv`), not `experimental.typedEnv` | `typedEnv` is experimental and generates types from the local `.env` only (nothing on a fresh clone/CI). `env.d.ts` is stable, committed, and documents the vars. |
| 2026-09-26 | Password reset **revokes all sessions** and **marks the email verified** | Reset is often done after a compromise; using the emailed link proves inbox ownership, so no second confirmation email |
| 2026-09-26 | **Multi-file Prisma schema** (`prisma/schema/`), one file per domain | Easier to navigate than one large file. Better Auth's CLI can only write one file, so all its models share `auth.prisma`. Runtime schema check uses the generated client, not the files, so it's unaffected. |
| 2026-09-26 | **`@@unique([organizationId, userId])` on `Member`** (hand-added in `auth.prisma`) | Better Auth only prevents duplicate memberships in code; now the database guarantees it. Verified the CLI keeps hand-added attributes when it rewrites the file. |
| 2026-09-26 | Remember the last workspace on the **user** (`lastActiveOrganizationId`), not the session | Each sign-in creates a new session, so a session field forgets it. Written from the workspace layout with `after()`, only when it changes. |
| 2026-09-26 | `proxy.ts` is **protect-by-default with a public allowlist**, one direction only (no cookie → `/sign-in`) | Workspace URLs are dynamic, so protected paths can't be listed. Redirecting signed-in users away from auth pages in the proxy would loop on expired cookies; pages do that with a real check. |
| 2026-09-26 | Invitation page readable **without signing in** (by its random id) | The invitee may have no account yet; the id only appears in their email, like a reset link. Accepting requires being signed in as the invited email (Better Auth). |
| 2026-09-26 | **Prettier config in the repo**, matching the editor settings | Same formatting for everyone and in CI; the one-time reformat is its own `style:` commit so it doesn't hide real changes |
| 2026-09-27 | shadcn **sidebar** for the app shell | Collapsible to icons, mobile drawer, keyboard shortcut and remembered state out of the box; standard SaaS look |
| 2026-09-27 | Working product name **"Billable"** in `utils/site.ts` | The landing page and titles need a name; one constant makes renaming trivial |
| 2026-09-27 | **Emerald** theme, buttons on emerald-700 | Fits a "get paid" product and stands out from blue SaaS apps; emerald-700 because white on emerald-600 fails WCAG AA |
| 2026-09-27 | **Cache Components stays off** | Nearly every page is per-user and per-workspace (reads the session cookie) and must be fresh; enabling it would mean Suspense boundaries around every session read for little gain, and more room for stale-data bugs in a multi-tenant app. Opt-in flag; can be revisited for public pages. |
| 2026-09-27 | **Composite foreign key** for tenant-owned relations (e.g. `Project(clientId, organizationId)` → `Client(id, organizationId)`) | The database, not just our code, guarantees related records belong to the same workspace (verified: cross-tenant insert rejected) |
| 2026-09-27 | **Clients: owners and admins create/edit/archive; members read only** | Members mostly track time; managing who gets invoiced is a management task. One line in `lib/permissions.ts` to change. |
| 2026-09-27 | Our resources are added to **Better Auth's access control** (`createAccessControl`), not a separate permission table | One definition of each role for Better Auth's checks and ours; typed permission names |
| 2026-09-27 | **Archiving a client archives its projects** (same timestamp) and restoring brings back exactly those | An archived client's projects shouldn't stay in active lists or get time; the shared timestamp remembers which ones to restore without an extra column |
| 2026-09-27 | Rates in **USD** until workspace settings existed (now: the workspace currency) | Invoices need the currency and business details anyway; one constant (`DEFAULT_CURRENCY`) to replace |
| 2026-09-27 | Project colors from a **fixed palette** of 8, not a free color picker | Consistent look, readable on light and dark, trivially validated on the server |
| 2026-09-27 | **One running timer per user across all workspaces**, enforced by a partial unique index | You work on one thing at a time; the database guarantees it even with two tabs racing. Starting a new timer stops the old one (like Toggl/Harvest). |
| 2026-09-27 | User time zone from a **browser-set cookie**, not a profile setting | Automatic, no settings page needed yet; server-rendered times and day boundaries match the user's clock. Can add a manual override later. |
| 2026-09-27 | Store `durationSec` as well as `startedAt`/`endedAt` | Reports and invoices just `SUM` it; a CHECK constraint keeps it consistent with `endedAt` |
| 2026-09-27 | Manual entries are **date + from/to**, not "date + duration" | Every entry keeps real start/end times (shown in lists, needed for the weekly grid and overlaps later); `durationSec` is still derived. A duration-only shortcut can be added to the form later. |
| 2026-09-27 | ~~Time-zone maths with `Intl` only~~ → **date-fns 4 + @date-fns/tz** (same day) | Needed for the weekly timesheet (week starts, day ranges in the user's zone). Widely known, tree-shakeable, official time-zone support; `TZDate` matched the hand-written version on every daylight-saving test. Temporal would be the built-in future option but isn't available everywhere yet. |
| 2026-09-27 | Timesheet shows **my own** time only; totals computed in JS from the week's entries | Matches "everyone tracks their own time"; a week of one person's entries is small, and day grouping reuses the same time-zone helpers as the list. Team totals live on the dashboard instead. |
| 2026-09-27 | PDF: **@react-pdf/renderer 4.9.0** (pinned) + embedded **Noto Sans** | The PDF is written as React components (same skills as the app, no headless browser); Noto Sans covers Latin/Cyrillic/Greek and fixes react-pdf's `€` width with the built-in Helvetica. Fonts ship via `outputFileTracingIncludes`. |
| 2026-09-27 | Billing settings in their **own table** (`WorkspaceSettings`, 1:1) | Better Auth's CLI owns and rewrites the `Organization` model; a separate table keeps our fields out of its way and is created on first save |
| 2026-09-27 | Invoices get their **number when sent**, from a row-locked counter | Deleted drafts leave no gaps in issued numbers (a legal requirement in many countries); the counter row lock makes concurrent sends sequential |
| 2026-09-27 | **Snapshots** of sender and client details on sending | An issued invoice must never change when a client's address or the business name is edited later |
| 2026-09-27 | **Overdue is computed**, not stored | It depends on today's date; storing it would need a job to flip it and could be stale. SENT + due date before today (viewer's calendar) |
| 2026-09-27 | **Void** keeps the invoice (and number) and **frees its time**; drafts can be deleted | Issued invoices are never deleted (records); the freed time can go on a corrected invoice |
| 2026-09-27 | No React Hook Form: the invoice editor uses **one Server Action per change** (lines in dialogs, details form) | Each change is saved and totals recalculated on the server, so there's no client state to keep in sync or lose; forms keep the `useActionState` pattern used everywhere else. RHF stays an option if a live multi-line editor is ever wanted. |
| 2026-09-27 | Invoices are for **owners and admins**; members get 404 | Financial data; consistent with who manages clients |
| 2026-09-27 | Public invoice link = **192-bit random token**, no sign-in | Clients shouldn't need an account (like a shared document link); unguessable, `noindex`, `no-referrer`; drafts never have one |
| 2026-09-27 | Payments go to **one platform Stripe account**, not Stripe Connect | Simple for a showcase, fully testable in test mode. A real product would use Stripe Connect so each freelancer is paid directly (onboarding, connected account id on the session); the payment code keeps the invoice/workspace in metadata so that's a contained change. |
| 2026-09-27 | **Hosted Stripe Checkout** + webhook, no Stripe.js/card fields in our pages | We never see card data (smallest PCI scope), no publishable key needed, Stripe handles 3-D Secure and local payment methods |
| 2026-09-27 | **Adaptive Pricing off** for invoice payments | An invoice is issued in its currency; Checkout converting it (with a ~4 % fee) surprises the client and breaks the amount check |
| 2026-09-27 | Record payments from **both** the webhook and the return URL, idempotently | The webhook is the reliable path (retried by Stripe); confirming on return shows "Paid" immediately. A unique Checkout session id makes double recording impossible. |
| 2026-09-27 | Payment reminders are **sent by hand**, at most **one per 24 h** per invoice | The freelancer decides when to nudge a client (a fixed schedule can feel pushy); the limit protects clients from double clicks and over-eager senders. A daily cron for automatic reminders can reuse `sendInvoiceReminder` later. |
| 2026-09-27 | Dashboard money is for **owners and admins**; members see their own hours | Same rule as invoices (financial data); a member's dashboard is still useful for their own time |
| 2026-09-27 | Revenue = invoices **paid** in the month (`paidAt`), in the workspace's currency only | Cash received is what a freelancer means by "revenue"; covers manual "mark as paid" as well as Stripe (the Payment table only has online payments). Summing different currencies would be meaningless, so others are listed, not added. |
| 2026-09-27 | Dashboard month boundaries computed in **JavaScript** and passed to SQL | Keeps all calendar/time-zone logic in date-fns (same as the rest of the app); Postgres' `AT TIME ZONE` would need its own time-zone names to match the browser's |
| 2026-09-27 | Demo = **a fresh sandbox per visitor** (own user + workspace from the same seed), deleted after 24 h; demo workspaces **never send email** | Chosen over a shared account with a nightly reset and a read-only demo: every feature works, even destructive ones, without visitors seeing each other's changes, and it shows off the multi-tenancy. Blocking email stops the demo being used to spam real addresses. |
| 2026-09-27 | Sandbox cleanup runs in **`after()` on each new demo**, not a cron | No scheduler to set up (works the same locally and on Vercel's free plan); visitors never wait for it; `MAX_SANDBOXES` caps the database even if nobody's sandbox expires |
| 2026-09-27 | A `DemoSandbox` **table** marks demo workspaces | Explicit and indexed (vs. guessing from slugs or emails); cleanup, the banner and the email block all ask the same question |
| 2026-09-27 | Demo data dated **relative to today** with a **seeded** random generator | Always current (this month's numbers, an overdue invoice, a running timer) yet reproducible for screenshots and debugging |
| 2026-09-27 | Unit tests in **`tests/unit/`** (rather than next to the code), pure logic only; no component tests | The risky logic (time zones, money, permissions) is plain functions: fast, exact tests. Next's docs note Vitest can't render async Server Components. |
| 2026-09-27 | `@types/node` **^24** (was ^20 from create-next-app) | Types should match the Node we run (24); Vitest 5 requires ≥ 22 |
| 2026-09-27 | Package-free helpers in a root **`utils/`** folder, the rest in `lib/` | Shows at a glance which code is plain logic (easy to test and reuse) and which depends on a library |
| 2026-09-27 | **No Playwright / end-to-end tests** | Unit tests + CI cover the logic; flows are checked by hand on a production build |
| 2026-09-27 | CI checks the **database** too: migrations on an empty Postgres, schema drift, seed | The most common "works on my machine" bug in Prisma projects is a schema change without its migration; an empty-database run also proves a fresh deploy works |
| 2026-09-28 | Migrations run in Vercel's build (`vercel-build`), **Production only** | Every deploy brings the database up to date with the code, with no manual step; previews share the production database, so they must not migrate it |
| 2026-09-27 | `tsx` for scripts (seed) | Runs TypeScript with the tsconfig `@/` alias and the generated Prisma client; Node's own type stripping handles neither. What Prisma's docs use for seeding. |
